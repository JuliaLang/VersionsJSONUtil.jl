## 2. Triggering a rebuild

To trigger a rebuild of the `versions.json` file and to upload it to S3, you need to manually trigger the `CI` workflow in this repo.
You can either trigger it through the GitHub UI or via an authenticated HTTP request.

### GitHub's UI

![grafik](https://user-images.githubusercontent.com/20866761/127783220-fd8167db-5051-4a18-b70a-ea42085a7cb5.png)

### HTTP request

```bash
curl \
  -u USERNAME:PERSONAL_ACCESS_TOKEN \
  -X POST \
  -H "Accept: application/vnd.github.v3+json" \
  https://api.github.com/repos/JuliaLang/VersionsJSONUtil.jl/actions/workflows/CI.yml/dispatches \
  -d '{"ref":"main"}'
```

Replace `USERNAME` with your GitHub username, and `PERSONAL_ACCESS_TOKEN` with a [personal access token](https://docs.github.com/en/github/authenticating-to-github/keeping-your-account-and-data-secure/creating-a-personal-access-token) with `repo` scope.

**Note that it is not possible to restrict personal access tokens to individual repos.**
**The token will have access to all repositories your GH account has access to.**
**Consider using a [machine user](https://docs.github.com/en/developers/overview/managing-deploy-keys#machine-users) solely created for this purpose.**

For more info, check the [GitHub Docs](https://docs.github.com/en/rest/reference/actions#create-a-workflow-dispatch-event).

## 3. `nightlies.json`

`nightlies.json` is generated by `VersionsJSONUtil.nightlies` in [`src/nightlies.jl`](../src/nightlies.jl) from
`HEAD` requests alone (nothing is downloaded). It probes the `julia-latest-*` URL of every platform in
`julia_platforms`, and of every build variant of every base platform, for `master` and for every `x.y` release
series that has a tag (plus the next two, so that a freshly created release branch is covered). Only files that
exist at generation time are listed: nightlies of inactive release branches expire from the bucket, so channels
come and go with release branches rather than with releases. That is why the `CI` workflow also runs on a daily
schedule; scheduled runs only rebuild and deploy `nightlies.json` and skip the full `versions.json` build. The
`Build nightlies.json` job is cheap enough to also run on pull requests, where it diffs its output against the
deployed file.

Its schema, [`schema-nightlies.json`](../schema-nightlies.json), duplicates the definitions of `schema.json`
(JSON Schema draft-06 has no way to compose object definitions that forbid additional properties). The package
tests check that the two do not drift: the `File` definitions must be identical except for the content-specific
keys (`version`, `size`, `sha256`, the tree hashes, `etag`, `last-modified`, and the inlined `asc`, which
`asc-url` replaces), `VariantFile` must be `File` plus the required `variants` list, and the enumerations must be
identical. When changing one schema, change the other accordingly.

### Adding a new build variant

Add its name and the base URL its builds are uploaded to to `nightly_variants` in
[`src/nightlies.jl`](../src/nightlies.jl). julia-buildkite names the artifacts of a variant by appending its name
to the OS, so the URL is `<base>/<os><variant>/<arch>/[<x.y>/]julia-latest-<os><variant>-<arch>.tar.gz`; add the
expected URL to the "Nightly download URLs" testset in [`test/runtests.jl`](../test/runtests.jl).

## 4. Adding a new platform

1. Add the version that introduces the platform to the `download_urls` dictionary in [`test/runtests.jl`](test/runtests.jl).
2. Add the platform the `julia_platforms` in [`src/VersionsJSONUtil.jl`](src/VersionsJSONUtil.jl).
3. Add any missing methods such as `tar_os` until all tests for the new platform pass.

### Example

For an example, adding the M1 MacOS binaries takes the following additions:

#### `test/runtests.jl`

```julia
const download_urls = Dict(
    v"1.7.0-beta3" => Dict(
        MacOS(:aarch64) =>              "https://julialang-s3.julialang.org/bin/mac/aarch64/1.7/julia-1.7.0-beta3-macaarch64.dmg",
    ),
    ...
)
```

#### `src/VersionsJSONUtil.jl`

```julia
julia_platforms = [
    ...
    MacOS(:aarch64),
    ...
]
```

and changing `tar_os(p::MacOS)` from

```julia
tar_os(p::MacOS) = "mac$(wordsize(p))"
```

to

```julia
function tar_os(p::MacOS)
    if arch(p) == :aarch64
        return "macaarch$(wordsize(p))"
    else
        return "mac$(wordsize(p))"
    end
end
```

## AWS authentication (GitHub OIDC)

The CI jobs that talk to AWS authenticate by assuming per-job IAM roles through GitHub's
OIDC provider, so no long-lived access keys are stored in this repo. Two roles with
different scopes are used; their ARNs are not secret (they are only assumable from this
repo's workflows) and are inlined in the workflow files:

- a **read-only role** (`arn:aws:iam::873569884612:role/VersionsJSONUtil-readonly`) for
  the `full-build-regular` job, which lists the `julialang2` bucket while building
  `versions.json`;
- a **deploy role** (`arn:aws:iam::873569884612:role/VersionsJSONUtil-deploy`) for the
  `upload-*-to-s3` and `deploy-schema` jobs, which write the four deployed files
  (`versions.json`, `versions-schema.json`, `nightlies.json`, `nightlies-schema.json`).

The GitHub OIDC identity provider (`token.actions.githubusercontent.com`) already exists
in the AWS account; the roles only reference it.

A note on pull requests: the read-only role is also assumable from `pull_request` runs of
this repo (their tokens carry the `sub` `repo:JuliaLang/VersionsJSONUtil.jl:pull_request`),
but only for PRs from branches of this repo — GitHub refuses `id-token: write` to
fork-triggered `pull_request` runs entirely, so fork PRs can never assume any role and
fall back to unsigned requests (which the public bucket accepts). The deploy role is not
assumable from PRs at all: its trust matches only `refs/heads/main`, and tokens minted for
`pull_request` runs carry a `sub` ending in `:pull_request` instead of a branch ref, so
even a future workflow mistake (like granting `id-token: write` to a PR job) could not
deploy from a PR.

### Managing the roles

The roles and their policies are defined with Terraform in [`terraform/`](../terraform/)
([`main.tf`](../terraform/main.tf)); the OIDC provider is shared with other repositories
and only looked up there, not managed. The state is kept in the `julialang-terraform` S3
bucket (`VersionsJSONUtil.jl.tfstate`). To review and apply changes, with
credentials for the AWS account active:

```bash
cd terraform
terraform init
terraform plan   # show what would change
terraform apply  # apply it (asks for confirmation)
```

Some notes on the definitions:

- The read-only role trusts `refs/heads/main` (push, and `workflow_dispatch`, which
  `full-build-regular` restricts to `main` with a matching `if:` guard), merge-queue refs
  (`refs/heads/gh-readonly-queue/...`), and `pull_request` runs as described above. It
  can list and read the `bin/` prefix: the build lists it to decide what is missing and
  downloads the binaries through authenticated requests (`s3:GetObject`), so neither part
  is subject to anonymous rate limits. Its maximum session duration of 6 h matches the
  `full-build-regular` job timeout: the job requests a 6 h session
  (`role-duration-seconds` in `CI.yml`) because a full rebuild runs for hours and the
  credentials must outlive it (the IAM default of 1 h would expire mid-build).
- The deploy role trusts exactly `refs/heads/main`, since deploys only ever run from
  there. It can write exactly the four deployed files (`s3:PutObjectAcl` is required
  because the uploads use `--acl public-read`).

Locally, `VersionsJSONUtil.main` sends unsigned requests when no AWS credentials are in
the environment, which the public bucket accepts.
